docs / install

Running a client

Clone, install, run. Auto-detects CUDA, ROCm, and MPS backends. Kills cleanly whenever you want.

Requirements

  • Python: 3.9 or newer
  • GPU: CUDA (NVIDIA), ROCm (AMD), or MPS (Apple Silicon). 8GB+ VRAM recommended.
  • RAM: 16GB minimum
  • Network: Stable connection, 20Mbps+ up/down (for weight transfers)
  • Storage: ~5GB for dataset chunks and checkpoints

CPU fallback works but is orders of magnitude slower. Useful for development and testing.

# Clone the repository $ git clone https://github.com/Vxtzq/CrowdGPT.git $ cd CrowdGPT # (Optional) virtual environment $ python -m venv venv && source venv/bin/activate # Install dependencies $ pip install -r requirements.txt

The client loops: fetch task, download data chunk from HuggingFace, train locally, compute delta, submit. Press Ctrl+C anytime to stop; graceful shutdown is handled.

Common flags

  • --mode quick: 500 local steps, fastest iteration
  • --mode balanced: 5000 local steps (default)
  • --mode deep: 50000 local steps, higher quality delta
  • --mode ultra: 100000 local steps, maximum contribution per task
  • --format bf16: bfloat16 transfer (default)
  • --format fp16: float16, slightly smaller payloads
  • --format fp8: fp8 quantization, smallest payloads
  • --username X --password Y: authenticate for leaderboard tracking

Account and leaderboard

Registering is optional. The client works anonymously. But if you create an account, your contributions, tokens processed, and trust score get tracked on the public leaderboard. Registration happens client-side against the coordinator's auth endpoint.

docs / protocol

How the protocol works

Federated learning with a central coordinator. Clients train locally, submit deltas, the coordinator aggregates.

Architecture

CrowdGPT uses a coordinator that holds global model weights and assigns training tasks to clients. This is classic federated learning, the same approach Google pioneered for keyboard prediction, now applied to language model pretraining.

The coordinator is a small Python application. The client is a single Python file (client.py). No opaque binaries, no hidden services.

Training loop

Each training step follows this sequence:

  1. Client calls GET /fl/task requesting work
  2. Coordinator assigns a data chunk (1MB of the training dataset) and returns current weights plus training config
  3. Client downloads the data chunk directly from HuggingFace (offloads bandwidth from the coordinator)
  4. Client trains locally for N steps (500, 5000, 50000, or 100000 depending on mode)
  5. Client computes weight delta (final weights minus initial weights)
  6. Client submits delta to POST /fl/submit
  7. Coordinator validates and applies the delta to global weights
  8. Coordinator checkpoints; client loops back to step 1

The model

Current architecture is a 500M parameter dense decoder-only transformer:

  • 1536 hidden dimension, 24 layers
  • 16 attention heads, 4 KV heads (grouped-query attention for efficient inference)
  • 96 head dimension, max sequence length 64
  • SwiGLU activations in the feed-forward layers
  • Rotary position embeddings (RoPE)
  • Weight tying between input embedding and output projection
  • Chunked attention to manage memory during training

This is the same architectural family as Llama, Mistral, and other modern open models, just scaled to run on consumer hardware.

The data

Training on the TinyStories dataset, pre-tokenized and binned into 1MB chunks, hosted on HuggingFace. The coordinator tracks position across the dataset so clients work on different chunks and don't repeat work. When the full dataset is covered, the epoch counter increments and training continues.

Aggregation

The coordinator uses sequential aggregation: as deltas arrive from clients, they're applied to the global weights with a configurable learning rate (default: 0.1). Weight decay (default: 1e-4) is applied on each step. The global weight norm is clipped to a maximum value to prevent runaway updates. 

w_new = w_old * (1 - decay) + delta * learning_rate
if ||w_new|| > max_norm:
    w_new = w_new * (max_norm / ||w_new||)

Consensus

The coordinator tracks which clients are working on which chunk and advances the chunk pointer when enough clients have contributed (default: 3). This is loose consensus; a solo client can still make progress on a chunk on their own. The system adapts to however many nodes are currently online.

Sanity checks

The coordinator validates every submitted delta before applying it:

  • NaN/Inf detection: malformed weights are rejected and the submitting subnet is flagged
  • Norm bounds: deltas that are too large for the number of local steps are either normalized or rejected
  • Size matching: deltas must match the exact parameter count of the global model

Quantization

Weights are transferred in compressed formats to reduce bandwidth:

  • bf16 (default): bfloat16, 2 bytes per param, ~1GB per transfer
  • fp16: float16, slightly better compression on some workloads
  • fp8: float8_e4m3fn, ~500MB per transfer, some precision loss

LoRA support

The protocol supports low-rank adaptation training. Clients can train a LoRA adapter at any rank from 32 up to full rank (2048). Lower-rank updates get weighted less during aggregation, reflecting their smaller expressive capacity.

Accounts and trust

Clients can optionally authenticate with a registered account. Per-user stats are tracked: contributions, tokens processed, training steps. A trust score is derived from contribution history and displayed on the leaderboard.

Checkpointing

The coordinator checkpoints global weights every 100 steps and retains the most recent checkpoints. Clients always resume from the latest checkpoint on startup, so progress is preserved across restarts.

Model architecture

The current architecture is a 500M parameter decoder-only transformer with the same building blocks as modern production language models.

  • Vocabulary: 50,257 tokens (GPT-2 tokenizer)
  • Hidden dim: 1536
  • Layers: 24
  • Attention heads: 16 (4 KV heads, grouped-query)
  • Head dimension: 96
  • Max sequence length: 64
  • Activations: SwiGLU
  • Position encoding: Rotary (RoPE)
  • Weight tying: input embedding to output projection

What's implemented

✓Full client-coordinator training loop with sequential aggregation
✓Hardware auto-detection: CUDA, ROCm, MPS, CPU fallback
✓Weight quantization (bf16, fp16, fp8) with fp32 coordinator-side storage
✓LoRA training at any rank from 32 to full rank (2048)
✓User accounts, authentication, and public leaderboard
✓Checkpointing with resume-from-latest on coordinator restart
✓Delta validation: NaN/Inf detection, norm bounds, size matching
✓Subnet-level rate limiting and banning for malicious submissions
✓Data position tracking across epochs to avoid redundant work

API endpoints

The coordinator exposes the following endpoints:

  • GET /fl/task: request a training task
  • POST /fl/submit: submit a weight delta
  • POST /auth/register: create an account
  • POST /auth/login: authenticate
  • GET /auth/me: current user info
  • GET /api/stats: global training statistics
  • GET /api/leaderboard: public leaderboard
  • GET /api/checkpoint: download current weights
  • GET /api/model_info: model configuration

Roadmap

Development is driven by contributors. Current areas of active work:

  • Scaling to larger parameter counts (7B+) with model sharding
  • Gradient compression for lower bandwidth usage
  • Optional TLS encryption between client and coordinator
  • More aggressive outlier detection on submitted deltas
  • Support for longer context lengths (128, 256, 512 tokens)
  • Improved consensus logic for high-churn scenarios

Why a coordinator instead of P2P?
Simplicity. A coordinator makes aggregation deterministic, coordination trivial, and debugging straightforward. P2P federated learning is a fascinating research problem, but a central coordinator is the pragmatic choice for actually shipping a working training run. The coordinator code is MIT licensed; anyone can fork it and build a P2P version if they want.
What's the network overhead per task?
In bf16 (default), each weight transfer is ~1GB. The client downloads the current weights, trains locally, then uploads the delta (same size). The data chunk is fetched from HuggingFace's CDN separately, so it doesn't hit the coordinator. With fp8 quantization, transfers drop to ~500MB each.
Can I run on CPU only?
Yes. The client falls back to CPU automatically when no GPU is detected. It works, it's just dramatically slower than GPU training. Useful for development, testing the protocol, or contributing whatever compute you have.
What hardware is recommended?
Minimum: 8GB VRAM GPU, 16GB RAM, stable 20Mbps+ connection. Recommended: 12GB+ VRAM GPU, 32GB RAM, fast connection (50Mbps+). Higher VRAM allows training at higher batch sizes and with longer local step counts.
How do you prevent poisoned deltas?
Every submitted delta goes through validation: NaN/Inf checks, norm bounds that scale with the number of local steps and the LoRA rank, and size matching against the global parameter count. Deltas that exceed the bounds are either normalized or rejected. Malicious subnets get banned.
Can I train on my own dataset?
Yes, if you host your own coordinator. The dataset URL is a configuration option. You can point it at any HuggingFace dataset or self-hosted binary file in the same format. The public instance uses TinyStories.
